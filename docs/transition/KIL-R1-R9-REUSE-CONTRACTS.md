# KIL R1–R9 reuse and contract matrix

## Purpose and assessed boundary

This record closes the coordination portion of [KIL issue #26](https://github.com/gatekeeper454/KIL/issues/26). It identifies what the assessed Kinetic Infrastructure Layer (KIL) source can contribute to an external deployment or component project, what it cannot establish, and the next compatibility gate for every candidate.

**Assessed KIL source:** [`da686bbc9f1360f6a806f78d3449184d1e3a8e99`](https://github.com/gatekeeper454/KIL/tree/da686bbc9f1360f6a806f78d3449184d1e3a8e99) (`main` when assessed).
**Canonical KTP basis:** [KTP v2.1.0](https://github.com/nmcitra/ktp-rfc/tree/v2.1.0), particularly its [Core](https://github.com/nmcitra/ktp-rfc/blob/v2.1.0/rfcs-md/ktp-core.md), [Enforce](https://github.com/nmcitra/ktp-rfc/blob/v2.1.0/rfcs-md/ktp-enforce.md), [Audit](https://github.com/nmcitra/ktp-rfc/blob/v2.1.0/rfcs-md/ktp-audit.md), [Transport](https://github.com/nmcitra/ktp-rfc/blob/v2.1.0/rfcs-md/ktp-transport.md), and [Kinetic Envelope](https://github.com/nmcitra/ktp-rfc/blob/v2.1.0/specifications/kinetic-envelope.md) contracts.
**Coordination input:** the [Blue Zone deployment guide's R1–R9 inventory](https://github.com/nmcitra/trust-physics-working/blob/main/ktp-blue-zones/docs/design-drafts/2026-09-16-cisco-blue-zone-deployment-guide.md#43-kil-reuse-accounting-before-any-new-kag-work). That guide remains deployment-owned; this is the KIL-side source record.

This is an assessed-source contract, not a perpetual public-API promise. It does not transfer ownership, amend the repository's [Apache-2.0 license](../../LICENSE), authorize copying beyond that license and applicable [NOTICE](../../NOTICE) obligations, require KIL to retain any interface, appoint a downstream owner, or qualify any deployment as production-ready. A downstream project must preserve applicable attribution and record its own source pin, compatibility tests, deployment configuration, owner, and acceptance evidence.

## Cross-cutting contract limits

### Two clocks, not one latency guarantee

KIL separates a slower authoritative signed-state refresh from faster per-action evaluation. A still-valid state can be evaluated without waiting for a new refresh; in the selected reducing mode, qualified fresh local evidence may only restrict or withhold that result. It cannot increase authority, clear a veto, expand the envelope, or extend expiry. This is an architectural separation, not a sub-second service-level guarantee. Any deployment must measure its end-to-end action path, including state/provider freshness, source delivery, adapter, recorder and target costs, and report missed bounds rather than infer performance from this source.

### Evidence classes remain distinct

KIL evidence labels require provenance appropriate to the class. The relevant records remain separate:

| Evidence class | What it supports | What it does not support |
| --- | --- | --- |
| **Modeled** | Deterministic historical replay inputs and conditional KIL decisions. | A reproduced historical prevention result, live provider behavior or deployment performance. |
| **Observed local Envoy boundary** | The accepted V3B-1 joined local result: `permit / permit / deny`, HTTP `200 / 200 / 403`, target markers `1 / 1 / 0`, with one attempt per driver. | Kind/Calico validation, production durability, deployed swarm containment, comprehensive bypass closure or historical prevention. The bundle remains `not_promoted`. |
| **Future live deployment evidence** | A separately executed, source-pinned deployment record with its own provider, route, target, latency, recovery and effect evidence. | Automatic inheritance from modeled or local-lab evidence. |

The [V2 progress record](../lab/V2-PROGRESS.md) limits historical replay to modeled counterfactual behavior. The [V3 progress record](../lab/V3-PROGRESS.md) and [Envoy adapter contract](../../adapters/envoy/README.md) limit the accepted run to an observed intermediate local-Envoy boundary. Neither permits a historical-prevention or deployed-containment claim.

## Consequential overlap and justified missing interfaces

The assessed KIL source already supplies candidate authorizer, verifier, constrained per-action evaluator, evidence-label, recorder-pattern and fixture functions. A Component Dev or deployment project should not create a second scorer, proof format, recorder, identity issuer or Envoy dependency merely because KIL exposes a similarly named laboratory surface.

The only justified unresolved interfaces are external to this KIL coordination record:

1. a real actor/trajectory/lineage provider and its attributable freshness/revocation contract (R4);
2. a protected ingress plus exact real-target binding, effect/idempotency/version and unknown-outcome reconciliation contract (R5);
3. durable shared reservation, recording, recovery and reconciliation semantics where a selected deployment needs them (R6); and
4. version-pinned provider/connector contracts for identity, context, inspection and storage (R9).

Each is **UNKNOWN** until a selected deployment demonstrates either compatible reuse/configuration or a concrete mismatch. A missing-interface claim must name the assessed candidate, exact mismatch, smallest correction, owner and acceptance test. This record authorizes no new KIL runtime engineering and does not assign implementation work to another project.

## Next acceptance gate

Before deployment readiness can be accepted, the consuming project must publish its source/package pins, selected R1–R9 dispositions (`reuse unchanged`, `configure`, `adapt`, `missing`, or `defer outside this pilot`), real input/output contracts, compatibility fixtures, owners and live evidence. Until then, this matrix is a source-backed reuse assessment only.
